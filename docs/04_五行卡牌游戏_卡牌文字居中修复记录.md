# 五行卡牌游戏：卡牌文字居中问题修复记录

修复文件：`ui/card_view.gd`（新增 16 行，其余代码未改动）

## 1. 问题现象

手牌中部分卡牌的**描述文字相对卡面明显偏右**，尾部还会被卡面右边框裁掉；而同一张牌在悬停放大的卡片上却是正常居中的。表现为逐张随机出现，一度被误判为扇形手牌两边的牌才会出问题。

## 2. 根本原因

`configure()` 在卡牌进入场景树之前就被调用：

```gdscript
# ui/battle_ui.gd
func _card_front(card: Dictionary, card_size: Vector2) -> Panel:
	var view: Panel = CARD_VIEW_SCENE.instantiate()
	view.call("configure", card, card_size.x)   # 此时卡还没入树
	return view                                  # 调用方才 add_child
```

于是 `CardView.configure()` 里创建 Label 时，卡与 Label 都不在场景树中。而：

```gdscript
label.size = dimensions     # Control.set_size() 会把尺寸夹到 get_combined_minimum_size()
```

Label 的最小尺寸等于文本自然宽度，该宽度由 `get_theme_font("font")` 决定。**不在树里就没有主题**，`get_theme_font` 静默回退到 Godot 内置字体，而非游戏主题的 PingFang SC。内置字体的汉字步进宽得多——同一句 11 字描述，主题字体下 113px，内置字体下 **163px**。

结果：设计好的盒子宽度 `206 × factor` 被向上撑大。8 张手牌时（设计宽度应为 **104.72**）实测为：

```text
138 / 131 / 163 / 170 / 131 / 131 / 131 / 115
```

盒子被撑宽后，`horizontal_alignment = CENTER` 让文字在这条过宽的盒子里居中，视觉上相对卡面**右移了撑大量的一半**（最多约 29px），尾部再被卡面的 `clip_contents` 裁掉。

## 3. 为什么表现为“逐张随机”

- 是否被撑，只取决于**该张牌自己的描述文字宽度**是否超过自己的盒子，与它在扇形中的位置无关。
- 手牌越多，盒子越小（122 < 132 < 152），越容易触发；描述越长越明显。
- 悬停放大卡为 270px，盒子 231.75 足够宽，因此从不触发——这正是“放大版正常、小卡不正常”的原因。

另经运行时清点场景树确认：7 张手牌 + 1 张悬停预览共 14 个卡牌视觉**全部**是 `ui/card_view.tscn` 实例，每张手牌带 4 个 Label，旋转施加在整张卡节点上（`rotation_degrees` + `pivot_offset`），文字随整张卡一起旋转。扇形手牌管理器没有实时绘制任何卡牌，牌面只有 `CardView.configure()` 一条构建路径。

## 4. 修复

`_add_label()`（`ui/card_view.gd:90`）只加一行，记录设计尺寸：

```gdscript
label.set_meta("designed_size", dimensions)
```

在卡牌进入场景树时重新落实设计尺寸——此刻主题已解析，自然宽度小于设计盒子，不再被夹：

```gdscript
func _ready() -> void:                                   # ui/card_view.gd:51
	_reapply_designed_sizes(self)

func _reapply_designed_sizes(node: Node) -> void:         # ui/card_view.gd:60
	for child in node.get_children():
		if child is Label and child.has_meta("designed_size"):
			child.size = child.get_meta("designed_size")
		_reapply_designed_sizes(child)
```

递归是必要的：牌背的「行」字挂在里层 `inset` 面板上，不是卡的直接子节点。

## 5. 验证方法

必须在**真实战斗场景**中验证，即保持游戏真实的“先 `configure()` 后入树”顺序。实测 5 / 7 / 8 张手牌共 20 张卡：`desc.size.x` 全部精确等于 `206 × factor`，消耗与属性标签墨迹全部存在。

**注意：测试脚本如果写成先 `add_child(card)` 再 `configure()`，等于提前入树，字体会是正确字体，夹取不会发生，测试会假通过。** 本次排查中曾因此得到“480 个标签 0 处不符”的错误结论。

## 6. 排查中被推翻的错误结论

| 结论 | 实际 |
| --- | --- |
| 扇形手牌不是预制体、是实时渲染 | 全部是 `card_view.tscn` 实例，见第 3 节 |
| 问题只出现在扇形两边的牌 | 与位置无关，取决于该牌描述文字宽度 |
| 给 Label 加 `clip_text = true` 可修复 | 治标。它让宽度不被夹，但同时把消耗/属性盒子压到 `28 × factor`（低于 `25 × factor` 字号所需行高），把字整个裁没。已撤销 |
| 调整 `_add_label` 内部赋值顺序可修复 | 治标。真正原因是 `configure()` 时无主题可用，与赋值顺序无关 |

## 7. 未处理事项

- **描述文字比几何中心偏左约 0.5%–2%**：由「，」「。」全角标点墨迹偏在字框左侧造成，属中文排版正常现象（未被改动的 270px 卡片偏移量相同）。不建议补偿。
- **敌方立绘遮住敌方手牌牌背**：`battle_ui.gd` 的 `_build_battle()` 中 `_build_arena_actor()` 排在 `_build_enemy_hand()` 之后，两者都挂在 BattleUI 上。经确认暂不处理。
- **`stretch/aspect` 未设置**（默认 `ignore`）：窗口非 16:9 时 UI 会被非等比拉伸。
- **缺少回归测试**：建议补充，但必须使用真实的“先 `configure()` 后入树”顺序。
